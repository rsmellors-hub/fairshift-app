# Subscription confirmation and workplace setup

## Scope

This change removes friction between subscription commitment and operational entry.
It enables an entitled Owner to establish the business and first operating location
needed for the commerce → forecast → staffing → worker-opportunity loop. It does
not implement downstream forecasting or staffing. Payment/account messages remain
truthful, supporting transparency, product coherence and presentation quality.
Financial authority remains in the existing subscription service.

## Journey and controls

`/billing/return` checks the existing server-authoritative subscription service.
An entitled organisation proceeds to `/onboarding`, or `/owner` if setup is already
complete. Neither browser return nor query parameters activate entitlement.
The confirmation UI exposes no provider identifiers or raw subscription state.

Automatic checks run sequentially, three seconds after the preceding result, up
to ten times. A secondary “Check payment status” control appears after 15 seconds.
Both paths use the same server action and existing reconciliation service. Neither
path creates subscriptions. Concurrent customer checks are prevented in the UI.
Recovery copy makes no unsupported statement about charges.

Progress is informational: Account → Plan → Workplace → Ready. There is no Team
step. Setup collects first/last name, job title, phone, business name, and the
first location's name, address, city, postcode and country. Verified email is
displayed as text. Honorific and region are not mandatory.

The same-address checkbox defaults checked. The server copies location address
data to the organisation in that case. Unchecking reveals independent business
address fields; these are validated and persisted separately. Existing profile,
business and location values prefill only their corresponding fields. Controlled
form values survive validation and server errors. Setup remains transactional and
retains the original location capacity check and separate completion marker.

## Migration

Generated by `pnpm db:generate`: `0010_lowly_red_ghost`.
SQL was inspected before application: five `ALTER TABLE outlets ADD COLUMN`
operations, all nullable `text`, with no defaults or backfill:

- `address`
- `city`
- `province` (optional; consistent with organisation address persistence)
- `postal_code`
- `country`

No IDs, ownership, relationships, limits, historical migrations or financial
columns change. Existing address-less locations remain valid. New workplace
completion validates the address in application code.
